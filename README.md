# Control

A local Rust control plane for federated agent workflows. Lenses are pure functions over explicit context snapshots: they select knowledge and tool descriptors, without ownership or authority. Personas guide behavior, policy bounds authority, and workflows describe control flow.

Run `cargo run --locked` and visit http://127.0.0.1:8080. `nix develop` provides the Rust toolchain. Rooms, reviews, chat, and the run ledger persist in `.control/state.json`, written atomically with private file permissions. Only one service instance should use a state directory. The web service never loads `.env`.

The UI includes lenses, rooms, a knowledge review inbox, an authority queue, a document editor, a run ledger, self-improvement proposals, and a Rust/WASM tool window. Website chat, agent tasks, and self-improvement proposals enqueue Codex container runs. Missing prerequisites produce blocked runs; there is no host fallback.

A node owns data and execution. A lens selects knowledge, tools, and instructions for a context. Effective tool access should be the intersection of lens selection, node policy, and user permissions. The current tool lists illustrate that model; they do not execute tools.

The server requires a loopback bind address, checks Host/Origin headers, and requires an operator session for every UI/API/asset route. On this laptop, run `cargo run -- open` to open the browser through a single-use local sign-in link. Operator credentials stay in private `.control/` files and are never passed to workers. Only `/health` is public. Tailscale publication and remote access remain unconfigured. For a background macOS service, build `cargo build --release --bins`, create `.control`, then load `hosting/dev.control.web.plist` with `launchctl bootstrap gui/$(id -u) hosting/dev.control.web.plist`. The supplied paths target this laptop. Unload with `launchctl bootout gui/$(id -u)/dev.control.web`.

Lenses are pure functions over explicit context snapshots, without node ownership. They select knowledge and tools; resource permissions are enforced separately.

Knowledge submissions require a concise claim, evidence, scope, and recheck condition. Exact case-insensitive duplicate claims are rejected while pending or accepted; semantic deduplication is not implemented. Accepted entries remain visible in the inbox and are not automatically injected into lens context. Authority decisions are manual records, including requests routed to an unconnected judge; they never grant host capabilities. Persona/workflow declarations remain reference schemas.

## Rust/WASM tool windows

`crates/context` contains the pure tool registry and selection logic, used by both the native inspector and compiled browser window. In `web/`, run `trunk build --release --locked`. The server serves generated assets at `/tool-window/`; the Tool windows view embeds the component. All UI logic is Rust. Trunk and wasm-bindgen generate browser interoperability code; there is no handwritten JavaScript application code. The inspector makes no effectful calls. Other execution endpoints remain unconnected.

## Codex container workers

Build `.#worker-image` on a Linux Nix builder and load the image into the laptop's container engine. The image is assembled directly with `dockerTools.buildLayeredImage`, without a distribution base. Configure `CONTROL_WORKER_IMAGE` (or `.control/worker-image-id`) with a content-addressed `sha256:<64 hex digits>` image ID or `name@sha256:<64 hex digits>`.

Sign in to Codex on the host with your ChatGPT account using `codex login`. Workers mount only the existing `auth.json` file read-only at `/home/agent/.codex/auth.json`; credentials are never copied into the image/workspace or passed through environment variables. The host control plane checks file metadata without reading its contents. The source defaults to `$CODEX_HOME/auth.json` or `~/.codex/auth.json`; `CONTROL_CODEX_AUTH_FILE` can override the non-secret path. The file must be a private regular file owned by a non-root user; symlinks and group/world permissions are rejected. If necessary, configure host Codex with `cli_auth_credentials_store = "file"` before signing in. Never print, paste, or commit the file.

The container runs as the credential file's non-root UID/GID. A named Codex permission profile denies agent tools access to the entire Codex state directory and disables tool network access. Each run first tests a separate empty auth canary: direct and proc-alias reads must fail, the tool supervisor must be inside its own PID namespace, and workspace writes must succeed. Verification failure blocks the run before mounting real credentials. `cargo run --locked -- --check-worker` exercises this path and one small authenticated model/tool task, reporting only a safe success/failure message.

The read-only mount cannot persist refreshed tokens. If authentication expires or token rotation requires a write, refresh the host Codex login and submit a new run; workers never make the credential mount writable. Account access remains subject to the plan's entitlements and limits. See the [official authentication documentation](https://learn.chatgpt.com/docs/auth). A broker that keeps provider credentials outside workers is planned in DESIGN.md.

The adapter uses a read-only container root, dropped capabilities, resource limits, ephemeral home, and a ten-minute deadline. Ordinary agent tasks receive an empty writable workspace, without Control source or configuration. Only an explicitly authorized architect improvement run receives a separate source snapshot. Worker credentials never include Discord or operator access. Snapshots omit `.env`, hidden files, symlinks, Git metadata, identity bindings, build outputs, and runtime state. Baseline and modified workspaces remain in `.control/runs/<id>/` for review. Changes never apply to the live source automatically.

An authenticated Codex run and sandboxed shell artifact were verified on this laptop on 2026-10-27 using the read-only account mount. Sandbox compatibility depends on the pinned Codex version and engine. The worker uses the [documented permission profiles](https://learn.chatgpt.com/docs/permissions), with no legacy `--sandbox` override. On this laptop, non-root bubblewrap requires Docker's proc masking disabled and a restricted seccomp profile with namespace/mount syscall allowances; all outer capabilities remain dropped, the container root stays read-only, and no privileged mode is used. See [hosting/worker-sandbox.md](hosting/worker-sandbox.md). Fine-grained harness network egress policy, independent validation, patch application, persistent conversations, and approval forwarding remain runtime work. Worker-reported checks are labeled as such.

## Discord bridge

The separate `control-discord` Rust binary supports direct messages from bound Discord user IDs. It is strictly DM-only: server-channel routing, reading, ingestion, replies, and jobs are disabled, including prefixed or mentioned messages. Send normal DM text to queue a task; send `hello`, `woof`, `help`, or `status` for an immediate built-in response. `/improve <objective>` and `!control improve <objective>` require architect access.

The bridge opens one-to-one DM channels only for locally bound IDs, verifies the channel type and recipient returned by Discord, and persists the confirmed mappings privately. It polls each conversation independently and replies to that same conversation. Private messages are not posted into the shared room. Recipient mappings and role policy are checked again at ingress and worker dispatch; a forged direct-message flag cannot bypass the policy. Bot/webhook messages and unexpected recipients are ignored. A plain-text task still runs in the user's isolated workspace; source access requires the architect's explicit improvement action.

The only required `.env` key is `DISCORD_TOKEN`. Non-secret identity bindings live in `discord-access.json`: geodesic is the architect, vivkelly and olliev are users. A label grants no access until its numeric snowflake ID is bound. Unknown identities/channels are denied. Bind IDs locally with `cargo run -- --bind-discord <label> <ID>`, or the bridge's `--bind <label> <ID>` command, without reading `.env`. Duplicate bindings and unexpected role assignments are rejected. Legacy channel configuration and channel-setting commands are rejected; `channel_id` must remain null. Legacy environment allowlist keys are ignored.

Run `cargo run --bin control-discord -- --check` to verify the bot and provision recipient channels without sending messages. Run with `--enable` to listen. Either explicit flag permits only the bridge process to load `.env`; running with neither does not read it. The bridge suppresses credential-bearing errors and disables automatic mentions in replies. Queued runs retain their actor identity; messages cannot supply their own role. Legacy runs without actor provenance are denied and must be resubmitted.

If Discord refuses to deliver a user DM, run `cargo run --bin control-discord -- --diagnose`. It reports only selected non-secret bot/application installation metadata, checks shared server membership with the architect, and supplies a zero-permission server installation link. It never emits raw API bodies or credentials. A listening bridge and a bot-side DM channel do not prove user-to-bot delivery. A shared server and compatible Discord privacy settings may still be required; installing Control there does not require moving the conversation out of DMs.

The bot needs access to the user's DM conversation; Discord privacy settings and app/server membership may affect messaging. The bridge skips historical messages on first activation, persists per-conversation cursors, deduplicates tasks by message ID, and backs off rate-limited reads. It is a REST-polling adapter, not a full Gateway or persistent-model-conversation implementation. Acknowledging a DM does not mean the worker is provisioned; missing worker authentication is reported back as a blocked run.

Server privacy has two layers: this application never requests server messages, while Discord permissions determine what the bot credential could access. A zero-permission invite still inherits permissions from @everyone and assigned roles. Use `--audit-server-permissions` to inspect effective role and channel overrides without reading any server messages. To deny server-text visibility at Discord's boundary, remove Administrator and explicitly deny View Channel for the bot member on categories/channels, including unsynced exceptions. A disabled Message Content intent alone is not an access boundary. DM access is independent of server channel visibility.

`hosting/dev.control.discord.plist` runs the bridge as a separate macOS user background service. Its service definition contains no token. The Integrations page reads a credential-free, freshness-checked status record and links to the bot's profile.

## Validation

Run `cargo test --locked --workspace` and `cargo clippy --locked --all-targets --workspace -- -D warnings`. Tests cover review transitions, knowledge duplicates, room isolation and escaping, pure lens behavior, image pin validation, Discord command parsing, and secret/symlink exclusion from snapshots. See [DESIGN.md](DESIGN.md) for the lightly edited prompts and filtered product direction, and [examples/engineer.nix](examples/engineer.nix) for the illustrative declaration schema.

Questions to resolve: Are agent runs pinned to a lens version? Which node is authoritative for cross-node writes? What retention rules should apply to rooms and evidence artifacts?
